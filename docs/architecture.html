🔍 seaglass — Architecture Reference

Local semantic + keyword search over iMessage history, exposed as an MCP server for Grogu. Generated as a living document — click through the pipeline, filter the eval table, and toggle detail levels below.

01 Overview

seaglass builds a local, offline search index over a user's iMessage history (~/Library/Messages/chat.db) and exposes it as an MCP server with two tools: search_messages and get_conversation. Grogu (the user's CLI agent) calls this server instead of doing raw SQL LIKE queries against chat.db directly, giving it real semantic recall ("what did we decide about the trip") on top of exact keyword matching, date-range/participant filtering, and conversation-level context expansion.

Design decision: no persistent daemon (yet). Each invocation pays a cold model-load cost (embedding model + cross-encoder reranker) and exits. This was an explicit, deliberate choice — see §7 Latency for the real measured cost of that decision, and why it may get revisited.

03 Runtimes & the chat.db lifecycle

Two things people ask about repeatedly: what actually executes the ML models, and how seaglass can safely read from chat.db — a database that Messages.app itself has open and is actively writing to — without corrupting it or racing a live write.

Runtimes

seaglass has no custom inference server or GPU runtime of its own. Both the embedding model and the cross-encoder reranker run in-process via Apple's MLX (seaglass/index/embed.py, seaglass/search/rerank.py) — MLX targets Apple Silicon's unified memory directly, so weights are loaded once per process and matmuls run on-GPU with no serialization/IPC round-trip to a separate server. There is deliberately no persistent daemon (see the design decision in §1): each MCP invocation is a fresh Python process that imports mlx.core, loads model weights from disk, and pays a one-time MLX kernel-compilation cost on the very first query (see the ~1.8s cold-invocation number in §10). Everything else — SQLite (index.db, chat_snapshot.db, live chat.db reads), the FastAPI app server, the MCP stdio server, and the pywebview desktop shell — is plain CPython; MLX is the only place the app leaves pure-Python/SQLite.

The one place GitHub Copilot CLI (GHCP) is invoked is not a runtime seaglass hosts itself — query-assist parsing and golden-set generation shell out to the copilot CLI binary as a subprocess (see §5 and §11); seaglass never talks to a model-serving API directly for those steps.

chat.db: snapshot during indexing, live afterwards

~/Library/Messages/chat.db is owned by Messages.app, which holds it open and writes to it continuously (new messages, read receipts, reactions). seaglass never opens a writable handle to it and never queries it directly during a full (re)build — instead:

Build/sync time — snapshot, then index the snapshot. run_build() (seaglass/app/indexstate.py) first copies chat_db_source (the live, real chat.db) to a private chat_snapshot.db file using SQLite's own online backup mechanism, taken via a short-lived read-only connection so Messages.app's writes are never blocked and the copy is always transactionally consistent. The entire embed → rerank → chunk → write pipeline then runs exclusively against that frozen snapshot, never the live file. This is what makes a build safe to run while iMessage is actively receiving texts, and it's also why index.db's content is only ever as fresh as the snapshot taken at the last build/sync.
After the build — live, read-only polling for staleness. Once an index exists, the running app needs to know how far the snapshot has drifted from reality without re-copying the whole database every time. SearchEngine.status() (seaglass/app/engine.py) opens a second, independent read-only connection directly to the live chat_db_source — via connect_readonly() (seaglass/imessage/source.py), which ATTACHes it under a file:...?mode=ro URI so it can never write — and compares its most recent message timestamp against the newest chunk already in index.db. This connection is cached and reused across polls (the status endpoint is hit roughly once a minute by the desktop UI) rather than re-attached every time, and it degrades to "unknown/0" rather than throwing if the live file is missing or unreadable (e.g. Full Disk Access revoked). This live connection is used only for counting how stale the index is — it is never used to actually pull message content into the index; that only ever happens against a fresh snapshot, via the same "Sync now" build path described above.

In short: chat_snapshot.db is the only thing the retrieval pipeline ever reads message bodies from, and it is only ever refreshed by taking a brand-new consistent snapshot of the live chat.db — the live file itself is touched only for cheap, read-only "how far behind are we" checks between builds, never for content.

04 Storage layer — index.db

A single SQLite file holds three cooperating tables per chunk plus two virtual (derived) indexes. No text is ever duplicated between them — full text lives compressed in chunks.body_semantic; the FTS5 index is contentless (inverted index only, no stored copy).

05 Query parsing

seaglass/search/parse.py turns a raw natural-language query into a ParsedQuery: a semantic text (fed to the embedder + BM25) plus structured extractions — date_from/date_to, has_media, and people_participant (chat participant handles, resolved via ContactIndex).

PatternExtracted asNotes
"last week", "in march"date_from / date_to Ambiguous bare month words ("may", "march") require corroboration (a digit or a second unambiguous date word elsewhere in the query) before being treated as a date.
"with Sam", "from Sam"people_participant Case-insensitivity is scoped to just the from|with keyword via inline (?i:...), not the whole pattern — needed so the capitalized-name heuristic still works.
"photo", "pic", "video"has_media = true Maps to the pre-computed chunks.has_attachment column.
Known simplification: "from X" (sender) and "with X" (participant) are not yet distinguished — both resolve to the broader "current chat membership" semantics. This can only make results too permissive, never miss a relevant chunk. Documented as a revisit-if-eval-shows-it-hurts-precision item.

06 Hybrid retrieval — dense + sparse, RRF fused

seaglass/search/retrieve.py implements the baseline retriever: a pre-filter followed by two independent candidate-generation paths, fused by Reciprocal Rank Fusion (RRF).

StageMechanismTop-K
Pre-filterSQL predicate over chunks (dates, media, participant chat_ids) — builds a candidate chunk_id set, or None meaning "unconstrained"—
Densesqlite-vec int8 cosine KNN over chunks_vec, constrained to the pre-filter set if present200
SparseFTS5 BM25 over chunks_fts (porter/unicode61 tokenizer), same constraint200
FuseReciprocal Rank Fusion, k=6050 (FUSED_TOP_K)
Note: FTS5's bm25() returns negative values — best matches sort ascending, the opposite of dense-search convention. Any code touching sparse scores directly has to account for this.
Note: sqlite-vec's int8 column type will silently misinterpret a bare blob parameter as float32 — every insert/query wraps the vector with vec_int8(...) explicitly.

07 Rerank + session aggregation

seaglass/search/rank.py + rerank.py — deliberately kept separate from retrieval so the baseline (no rerank) and full pipeline could be evaluated independently against the golden set.

  1. Cross-encoder rerank (ms-marco-MiniLM-L-12-v2) scores each of the 50 fused candidates against the query text directly (not just embedding similarity), cut to top 12 (RERANK_TOP_K). The model is run in eval mode for deterministic scoring.
  2. Session aggregation groups the top-12 reranked chunks by (chat_id, local calendar day) — approximating "that day we talked about X" — into up to 8 sessions (MAX_SESSIONS), combining member-chunk scores per session.
  3. Expansion pads each session with ±2 time-adjacent chunks (EXPANSION_RADIUS) for conversational context, even if those chunks weren't independently retrieved.
Day-boundary grouping uses the local system timezone, not UTC — a deliberate judgment call since chat.db timestamps carry no stored timezone of their own, and local wall-clock day is the closest approximation to how a person actually remembers a conversation.

08 MCP server surface

seaglass/mcp_server.py exposes three tools over stdio, single-process, guarded by a global lock (_pipeline_lock) since MLX has no cross-thread safety guarantee, plus a separate _init_lock around all lazy singleton getters (index connection, chat connection, embedding model, reranker, contact index).

ToolPurposeKey params
search_messagesRanked, hydrated conversation sessions with message-id citations for a topical/semantic queryquery, max_sessions=8, redact=false
get_conversationDrill-down: raw messages from one chat_id, optionally centered on a timestampchat_id, around_ts, limit=50
index_statusChunk/vector counts, configured DB paths, hydration/contacts availability — lets a caller sanity-check the index before trusting search results—
Behavior note: get_conversation's around_ts path searches the whole chat by fetching cheap (ROWID, date) pairs, locating the closest position to the target timestamp in Python, then fetching just that window by ROWID — so drilling into an old thread in a long chat still finds the right window regardless of chat length.

09 Grogu integration

Grogu (src/grogu_mcp.py + src/grogu_imessage.py) launches seaglass-mcp as a stdio subprocess per invocation, configured via ~/.copilot/mcp-config.json (which supplies SEAGLASS_INDEX_DB and SEAGLASS_CHAT_DB as environment variables to the subprocess). If seaglass is available, search_via_seaglass is preferred over the legacy SQL LIKE fallback.

search_via_seaglass requests seaglass's default max_sessions=8 regardless of the caller's message limit, and flattens each returned session's messages plus context_messages into one result list. The SQL LIKE fallback path normalizes Apple-epoch timestamps to unix seconds so both paths return dates in the same format.

grogu imessage status reports whether seaglass is configured and reachable (seaglass: true/false); grogu imessage search transparently uses seaglass when available and falls back to SQL LIKE otherwise.

12 CLI & operational commands

# build (or resume) an index from a chat.db snapshot
python -m seaglass.cli build <chat.db> <index.db>

# ad-hoc search from the terminal (bypasses MCP, same pipeline)
python -m seaglass.cli search <index.db> "lisbon trip" --chat-db <chat.db>

# score a golden set against a built index
python -m seaglass.eval.score <index.db> <golden.jsonl> --chat-db <chat.db>

# run as an MCP server (what Grogu launches as a subprocess)
seaglass-mcp   # entry point: seaglass.mcp_server:main
  # env: SEAGLASS_INDEX_DB, SEAGLASS_CHAT_DB
